# Brief

## Project

Restructure the existing single-module `sequeless-filter` Maven project (currently one `jar`-packaged root pom with `org.sequeless.filter.api`, `org.sequeless.filter.internal`, and `org.sequeless.filter.spi` packages under one `src/main`/`src/test`) into a multi-module Maven build with ArchUnit rules guarding module/package structure.

1. **filter-core module** — retains the current `api`, `internal`, and `spi` packages and their existing main-scope responsibilities (AST model, ANTLR grammar/parser, completion engine, operator/field registry contracts), with one scope change:
   - `DefaultFieldRegistry` and `PermissiveFieldRegistry` (currently `org.sequeless.filter.internal`) move out of `src/main` entirely and become an in-memory `FieldRegistry` adapter fixture living only in filter-core's test scope, for use by filter-core's own tests.
   - The `FieldRegistry` interface's static factory methods (`of(List<FieldDefinition>)` and `permissive()`) are removed from the api, since their backing implementations no longer exist in main scope. Beyond just removing the two factory methods, the `FieldRegistry` interface's remaining contract (including `isPermissive()`) should be reconsidered for necessity now that no production implementation ships a permissive mode — do not assume the rest of the interface is untouched.
   - `DefaultOperatorRegistry`, `BuiltinOperatorContributor`, `CursorAnalyzer`, `FilterBuildingVisitor`, and the generated ANTLR `internal.parser` package all remain in filter-core main scope, unchanged. They are load-bearing for `FilterParser.parse()`/`parsePartial()` and for `OperatorRegistry.defaults()`/`of()` to keep working in production — only the field-registry defaults move to test. (`OperatorRegistry`'s built-in operator vocabulary is module-shipped and stays a real production capability; `FieldRegistry`'s defaults are domain-specific sample data and become test-only.)
   - ArchUnit rules must guard this: `internal` stays inaccessible from outside filter-core, and the test-only field-registry fixture must not leak into any module's main/compile scope.

2. **filter-sql-adapter module (new)** — a SQL rendering layer that translates parsed `FilterNode` ASTs (produced by filter-core) into SQL, exposing its own API/SPI so downstream vendor-specific SQL adapters (e.g. Postgres, MySQL, Oracle) can plug in dialect-specific behavior. Depends on filter-core's main-scope api (and spi as needed) — never on filter-core's test-only fixtures.
   - An H2-backed implementation of the new SQL adapter SPI is provided as a **test fixture** of filter-sql-adapter (i.e. in its test scope, not shipped as a production artifact), used to validate SQL generation against a real embedded H2 database in tests.

3. Both modules are ArchUnit-guarded: rules enforce the intended package/module layering (e.g. `internal` packages not depended on from outside their own module, api packages depending only on other api/spi packages, test-only fixtures never leaking into any main/compile scope) and fail the build on violation.

- Status: Needs Answer
- Kind: Decision
- Description: With `permissive()`/`PermissiveFieldRegistry` moving to test-only and no production `FieldRegistry` implementation shipping a permissive mode, should `FieldRegistry.isPermissive()` be removed from the interface, kept as-is for implementors outside this codebase (e.g. a vendor-supplied registry) to still express, or changed in some other way?
